Manual Integration Test: Simple Non-Draft CRUD

DESCRIPTION

Test the simple create, delete and modify operations (without draft handling) on sales orders using an OData V4 binding with a deferred update group (updateGroupId update). A new sales order is created via a dialog; all changes are collected locally and are only sent to the back end when the Save button is pressed (submitBatch), or discarded when the Cancel button is pressed (resetChanges). The toolbar Save and Cancel buttons are always enabled and give feedback via a message toast, including when there are no pending changes. Verify that the create dialog, note modification and deletion behave correctly, that Cancel reverts every pending change, and that Save persists them in a single batch. The toolbar also offers a Refresh button which reloads the data from the back end, but is blocked by a message box while there are pending changes; it is only possible once all pending changes have been discarded.

PREPARATION

To check console errors open the developer tools before starting the application and check with each step, that there are no errors and warnings.

Testing with mock data

Start the application (this is the realOData=false case, served by a mock server): SimpleNonDraft
Note: The mock server responds almost instantly. To observe the view's busy state during the save operation, append &autoRespondAfter=1000 (delay per mock response in milliseconds) to the URL: SimpleNonDraft (delayed mock responses)

Testing with real data

To run against the real EPM back-end service (requires an SAP-internal reverse proxy that routes /sap/opu/odata4/... to the back end) append &realOData=true to the URL: SimpleNonDraft (realOData=true)

REALIZE and CHECK

Scenario 1: Initial Load and Empty-State Feedback

  1. Open the application URL from the Testing with mock data section above.
  2. Check: The table contains the two sales orders provided by the mock server: 0500000000 and 0500000001.
  3. While there are no pending changes, press the Save button in the toolbar.
  4. Check: A message toast appears with the text No changes to save. The view does not turn busy and no request is sent to the back end.
  5. Press the Cancel button in the toolbar.
  6. Check: A message toast appears with the text No changes to cancel. The table stays unchanged and no request is sent to the back end.

Scenario 2: Create Dialog - Cancel Discards the Transient Row

  1. Press the Create button in the toolbar.
  2. Check: A dialog titled Create New Sales Order opens with an empty, required Buyer ID input, a required Currency input defaulting to EUR, and the buttons Confirm (emphasized) and Cancel.
  3. Check: An empty transient row has already been prepended at the top of the table — the create call adds it immediately, before the dialog is confirmed.
  4. Press the Cancel button inside the dialog.
  5. Check: The dialog closes and the transient row is removed again, leaving the two original rows. Pressing the toolbar Cancel now shows No changes to cancel, confirming no residual pending changes.

Scenario 3: Rollback Flow - Create, Modify and Delete, then Cancel

  1. Press Create, enter 0100000001 into the Buyer ID input, leave Currency at EUR and press Confirm.
  2. Check: The dialog closes and the transient row stays at the top, showing (0100000001) in the Buyer column (the company name is only resolved after saving) and EUR as Currency; its Sales Order ID, Gross Amount and Lifecycle Status cells are still empty.
  3. In the row of sales order 0500000000, set the Note to Modified note.
  4. Check: The entered text stays in the Note cell.
  5. Select sales order 0500000001.
  6. Check: The Delete button becomes enabled.
  7. Press the Delete button.
  8. Check: Sales order 0500000001 disappears from the table immediately and the Delete button becomes disabled again (no row is selected anymore).
  9. Press the Cancel button in the toolbar.
  10. Check: A message toast appears with the text Changes have been canceled.
  11. Check: The transient created row is removed, the Note of 0500000000 reverts to its original value, and 0500000001 reappears — the table is back to the baseline from Scenario 1 and no request was sent to the back end.

Scenario 4: Persist Flow - Same Preparation, then Save

  1. Repeat the preparation from Scenario 3: press Create, enter 0100000001 and press Confirm; set the Note of 0500000000 to Modified note; then select and Delete sales order 0500000001.
  2. Press the Refresh button in the toolbar while the create, note and delete changes are still pending.
  3. Check: A message box (MessageBox.alert) appears with the text Refresh not possible with pending changes. Dismiss it by pressing OK; the pending changes are kept.
  4. Press the Save button in the toolbar.
  5. Check: The view is shown busy briefly while the batch request is in flight. Use the autoRespondAfter URL parameter (see PREPARATION) to slow the mock responses down enough to observe the busy state.
  6. Check: A message toast appears with the text Changes have been saved.
  7. Check: The created row now shows the server-assigned Sales Order ID which is 0500000002, the company name Becker Berlin next to buyer ID 0100000001, a Gross Amount of 0.00, the Currency is EUR and the Lifecycle Status is New.
  8. Check: The modified note on 0500000000 is kept and 0500000001 does not reappear — all three changes were persisted in a single batch.
  9. Press the Refresh button in the toolbar.
  10. Check: A message toast appears with the text Data refreshed. All data and modifications persist, but the row order changes: the created sales order 0500000002, which was shown at the top before the refresh, now moves to the bottom of the table because the server returns it as the last entity. The modified Note on 0500000000 is still shown, and 0500000001 remains deleted and does not reappear.

Scenario 5: Save Flow - Back-End Error on Create

  1. Press Create, enter an invalid Buyer ID such as 123 (no business partner exists for this key), leave Currency at EUR and press Confirm.
  2. Check: The dialog closes and the transient row stays at the top of the table showing (123) in the Buyer column.
  3. Press the Save button in the toolbar.
  4. Check: The back end rejects the creation. An error popup (MessageBox.error) appears describing the actual back-end error, i.e. with the text Business Partner with key '123' does not exist. No Changes have been saved message toast is shown.
  5. Check: After closing the popup, the invalid row is still present at the top of the table as a pending change — the view is no longer busy.
  6. Select the invalid row and press the Delete button to discard the failed creation.
  7. Check: The invalid row disappears from the table. Pressing the toolbar Cancel now shows No changes to cancel, confirming no residual pending changes remain, and the table is back to the previous state.
